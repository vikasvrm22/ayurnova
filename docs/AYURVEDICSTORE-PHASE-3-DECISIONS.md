# AyurvedicStore — Phase 3 Decisions Lock
## Ayurveda Discovery & Knowledge

**Type:** Architecture decision lock — no code modified. Validates the five proposed decisions against `docs/AYURVEDICSTORE-PHASE-3-AUDIT.md` and the actual current schema/API/CMS/frontend.

---

## Validation notes (evidence checked this pass)

- **Live category data is empty today.** `GET /api/public/categories` on the running instance returns exactly one row — the DEV-harness diagnostic fixture (`type: "concern"`). There is no real `concern`, `benefit`, or `product_type` content in the database yet; the "Health Concern"/"Product Type" filters in `shop.html` were always static mockup labels, never backed by real rows. This means restructuring how `concern`/`benefit` are stored carries **zero live-data migration risk** — it's greenfield.
- **No SEO/breadcrumb code depends on `category_id`.** Checked `server/src/seo/seoHelpers.js` directly — it has no category logic at all. The only current consumers of `products.category_id` are `admin/product-form.html` (one `<select>`) and `catalogService.js`'s filter. Narrowing what `category_id` means going forward is low-coupling.
- **`unique (a, b)` table-constraint style is already established** (`supabase/migrations/0002_phase2_payments_and_integrations.sql`, e.g. `unique (provider, environment)`, `unique (gateway, event_id)`) — new join tables should follow this exact convention.
- **Single-brand is trivially satisfied for comparison**: `products.brand` is a free-text field but every real row shares one value (the store's own brand) — there is no vendor/seller field anywhere in `products`/`orders`, so "cross-product comparison" has no marketplace dimension to guard against; it's inherently comparison within one brand's own catalog.

## Final Decision Table

| # | Decision | Final Recommendation | Reason | Implementation Impact |
|---|---|---|---|---|
| 1 | **Category structure** | **Approved as proposed, with one refinement.** Keep `products.category_id` but narrow its meaning to **`product_type` only** (Tablet/Oil/Churna/Syrup — genuinely single-valued, a product IS one type). Add two new many-to-many join tables, `product_concerns(product_id, concern_id)` and `product_benefits(product_id, benefit_id)`, referencing `categories` rows of type `concern`/`benefit` respectively (or one generalized `product_categories(product_id, category_id)` table if a single join table is preferred — either is additive and equally minimal). | A product needing >1 concern/benefit is the exact structural gap the audit identified; `category_id` is a single FK and cannot represent that. `product_type` (Tablet vs Oil) is inherently exclusive, so it's the one taxonomy dimension that correctly stays single-valued and keeps the existing admin `<select>` working unchanged. Zero live rows exist yet, so this is a clean cut, not a migration. | New tables: `product_concerns`, `product_benefits` (`unique (product_id, X_id)`, `on delete cascade` on both FKs, matching Phase 2's constraint style). `catalogService.js`'s `?concern=`/`?benefit=` filters change their internal join (category_id equality → `EXISTS` against the new tables) but **keep the same query-parameter contract**, so the public API shape (and Android readiness) is unaffected. `categories` gains `description`, `hero_image`, `seo_title`, `seo_description` (per the audit) so a concern/benefit slug can back a real landing page. Admin needs a new category CRUD page (categories.js's API already exists, §3.3 of the audit) plus a multi-select relationship editor in `product-form.html` replacing the single `<select>` for concern/benefit (product_type stays a single `<select>`). |
| 2 | **Goals vs Benefits** | **Approved as proposed.** Add `'goal'` to `categories.type`'s check constraint alongside a new `product_goals(product_id, goal_id)` join table, built identically to `product_benefits`. | Genuinely undefined in the current codebase (audit confirmed zero prior occurrences) — the proposed split (Benefit = what the product/ingredient does; Goal = what the shopper is trying to achieve) is a coherent, defensible content model and doesn't collide with anything existing. Purely additive: widening a check constraint is the same low-risk pattern Phase 2 used for `orders.payment_status`. | One constraint widen + one join table, identical shape to Concern/Benefit. **Caution (not a blocker):** Goal and Benefit will likely overlap in practice (e.g. "Better Sleep" fits both) — this is a content-curation/editorial-guideline concern for whoever tags products, not a schema or architecture issue. No code change mitigates it; a short internal tagging guideline for admin staff is the only real fix, and is out of scope for this decision lock. |
| 3 | **FAQs (global + product-specific)** | **Approved as proposed.** Single `faqs(id, question, answer, product_id nullable, sort_order, status)` table; `product_id null` = global/site FAQ, `product_id` set = product-specific. | One table cleanly serves both scopes without duplicating structure, and nullable FKs are already an established pattern in this schema (`orders.customer_id` nullable for guest checkout, `reviews.customer_id` nullable). Avoids the unnecessary complexity of two separate tables for what is structurally the same entity. | New `faqs` table (`product_id uuid references products(id) on delete cascade`, nullable). Admin CRUD reusing the `manageProducts` RBAC permission (same permission `categories.js` already uses — no new permission needed, consistent with "don't invent unnecessary features"). Public API: `GET /api/public/faqs` (global, `product_id is null`) and `GET /api/public/products/:slug` response gains a `faqs` array (product-scoped), following `catalogPublic.js`'s existing envelope. |
| 4 | **Product comparison** | **Approved as proposed, with an explicit sequencing note.** Cross-product comparison, single-brand only (trivially true — no seller field exists to guard against), using a defined attribute set: price, MRP, pack size/weight, stock/availability, average rating, review count, and — once Decision 1 lands — structured ingredients and concern/benefit tags. No new persistent schema needed; this is a read-only aggregation. | Matches the proposal exactly; single-brand is automatically satisfied since no vendor concept exists anywhere in the schema. Comparing only price/rating/weight (available today) would be technically buildable immediately but of limited real value — the ingredient/concern/benefit dimensions from Decision 1 are what make Ayurvedic product comparison actually meaningful to a shopper. | **Depends on Decision 1 being implemented first** to be worth building (not a conflict — a sequencing dependency). No new table required: a new `GET /api/public/products/compare?ids=a,b,c` endpoint in `catalogPublic.js`'s existing style, returning each product's comparable-attribute set side by side. Public UI: a new comparison view/page, out of scope for this decision lock. |
| 5 | **Search coverage** | **Approved as proposed, with an explicit sequencing note.** Plan search to eventually cover products, ingredients, concerns, and benefits (via `ilike` against structured entity names once Decision 1's tables exist, mapped back to products through the new join tables) — still plain deterministic SQL matching, no ranking/AI. Separately: **wire the existing, currently non-functional header `<form>` to the already-working `/api/public/search?q=` (title-only) now** — this closes part of the "disconnected UI promise" gap immediately and doesn't need to wait for Decision 1. | Matches the proposal's intent. Full concern/ingredient search breadth is structurally impossible before those entities exist (Decision 1), so it's a real dependency, not an oversight. The UI-wiring gap, however, is independent of any schema decision and is pure front-end work against an endpoint that already works today. | Two impacts, split explicitly by sequencing: (a) **now, independent of Phase 3 schema** — wire `header-search` forms to `/api/public/search?q=` across all pages (`public-site/js/site.js` currently has zero search code). (b) **after Decision 1** — extend `catalogService.js`'s search query to also `ilike` against `ingredients.name`/`categories.name` (concern/benefit) and union/rank matches back to products via the new join tables; update the search placeholder text to stop over-promising until this lands, or land it before changing the copy. |

## READY / NOT READY

**READY to begin Phase 3 implementation.**

All five decisions are approved as proposed (one with a minor refinement on Decision 1's exact split, two with sequencing notes on Decisions 4 and 5 rather than conflicts). None require inventing new capability beyond what was already scoped in the audit, none introduce AI/ML/LLM logic, none introduce marketplace/seller concepts, and every schema addition is additive (`categories` constraint widen + new join/FAQ tables) against a live database that currently holds no real category data to migrate. The recommended build order is the same as the audit's §5, now unblocked:

1. Schema: `product_concerns`, `product_benefits`, `product_goals`, `product_ingredients`, `faqs`, `categories` content-field additions, `categories.type` widened to include `'goal'`.
2. Admin CMS: category CRUD page, ingredient CRUD, multi-select relationship editor on `product-form.html`, FAQ CRUD.
3. Public API (`catalogPublic.js` pattern): `/ingredients`, `/ingredients/:slug`, `/faqs`, richer `/categories/:slug`, multi-value concern/benefit/goal filtering, `/products/compare`.
4. Public UI: wire `shop.html`'s existing filter sidebar to real query params, wire header search, build ingredient/concern/benefit/goal landing pages, public blog/knowledge-hub pages, FAQ section, comparison view.
5. SEO cleanup of the hardcoded homepage mega-menu links once real slugs exist.

Quick win available immediately, independent of the above sequence: wiring the header search form to the already-working title-only `/api/public/search` endpoint.
